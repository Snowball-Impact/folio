# AI 협업 성장 회고

이 문서는 FOLIO를 만드는 과정에서 드러난 협업 방식과 제품 개발 역량을 기록한다. 시간이 지난 뒤 같은 기준으로 다시 돌아보며 무엇이 성장했는지 확인하기 위한 스냅샷이다.

> 이 평가는 2026년 7월 7일까지의 FOLIO 작업 대화를 바탕으로 한 AI의 관찰이다. 정식 직무 평가가 아니며, 실제 경력이나 모든 역량을 단정하지 않는다.

## 2026-07-07 기준 관찰

### 현재 인상

기획과 디자인 감각이 강한 **프로덕트형 실무자**에 가깝다. 전통적인 역할 하나로 한정하기보다는 프로덕트 디자이너, 서비스 기획자, PM·PO, 프론트엔드 이해도가 높은 1인 제작자의 특성이 함께 보인다.

코드를 직접 많이 작성하는 유형이라기보다, 기술을 이해하고 적절히 위임하면서 제품의 완성도를 끝까지 끌어가는 **디렉터형 빌더**라는 인상이 강하다.

### 확인된 강점

- 화면의 여백, 정렬, 정보 위계와 페이지 간 일관성 문제를 빠르게 발견한다.
- 단순히 보기 좋은 화면보다 사용자 흐름과 정보 구조를 기준으로 개선을 요청한다.
- 작은 수정이 반복해서 실패하면 보정값을 더 쌓기보다 구조적 원인을 의심한다.
- 구현 결과를 직접 확인하고, 증거와 실제 화면을 기준으로 다음 피드백을 준다.
- AI별 작업 범위와 권한을 구분해 동시 작업의 충돌 가능성을 관리한다.
- 구현 이후에도 아키텍처, 데이터 모델, 사용자 흐름, 정책과 인수인계 문서를 챙긴다.
- 프레임워크 한계와 유지보수 비용을 인식하고 과도한 CSS 수정을 중단할 줄 안다.
- 만족 기준에 도달했을 때 명확하게 작업을 종료하고 다음 우선순위로 이동한다.

### 협업 방식 평가

요구사항을 구체적으로 전달하고 결과를 확인한 뒤 단계적으로 정밀도를 높였다. 특히 “진단과 확인을 우선하고 수정은 승인 후 진행”, “다른 작업자와 범위를 겹치지 않게 진행”처럼 작업 권한과 경계를 명시한 점은 성숙한 협업 방식이다.

초기에는 감각적인 표현으로 시작한 요청도 있었지만, 작업이 진행될수록 위치·간격·정보 구조·완료 상태가 더 명확해졌다. 이는 결과를 보며 요구사항을 구체화하는 능력이 빠르게 발달했다는 신호다.

### 다음 성장 포인트

- 구현 전에 사용자 결과와 완료 기준을 한두 문장으로 먼저 고정한다.
- “오른쪽으로 이동”보다 기준선, 간격, 반응형 동작처럼 검증 가능한 조건을 함께 제시한다.
- 기능별 우선순위뿐 아니라 실패했을 때의 사용자 경험과 예외 상태도 초기에 정의한다.
- 중요한 결정은 선택 이유, 버린 대안, 검증 결과까지 연결해 포트폴리오 서사로 남긴다.
- AI가 제안한 해결책을 승인할 때 유지보수 비용과 테스트 방법을 한 번 더 질문한다.

## 다음 회고에서 비교할 질문

1. 작업 시작 전에 완료 기준을 얼마나 명확히 정의하는가?
2. UI 피드백이 취향을 넘어 사용자 문제와 데이터로 설명되는가?
3. 정상 흐름뿐 아니라 오류·빈 상태·모바일까지 먼저 고려하는가?
4. AI 작업을 작은 수정이 아니라 역할과 책임 단위로 위임하는가?
5. 기술적 선택의 장단점을 스스로 설명하고 반대 의견을 검토하는가?
6. 결과물을 제품 문제, 의사결정, 검증, 학습의 이야기로 정리할 수 있는가?

## 2026-08-01 기준 관찰

### 달라진 점

제품의 시각 기준이 더 또렷해졌다. 이번 작업에서는 홈 갤러리, 프로젝트 상세, 등록 페이지, 마이페이지를 오가며 "깔끔하게 정리된 화면", "필요한 컴포넌트만 쓰는 화면", "본문과 같은 폰트 스타일과 사이즈"를 반복 기준으로 삼았다. 단순히 더 예쁘게 만드는 요청이 아니라 페이지 간 레이아웃, 여백, 카드 비율, 칩 정렬, 모바일 동작까지 하나의 제품 톤으로 묶으려는 방향이 강해졌다.

특히 중요한 변화는 문제가 반복될 때 "CSS만 바꾸지 말고 구조와 Streamlit wrapper를 확인하라"고 요구한 점이다. 이것은 UI를 픽셀 단위로만 보정하는 단계에서 벗어나, 프레임워크가 실제 DOM을 어떻게 만들고 있는지까지 확인하려는 태도다.

### 새로 확인된 강점

- 작은 어긋남을 발견하되, 몇 번의 수정이 빗나가면 구조적 원인을 요구한다.
- 홈 갤러리처럼 마음에 드는 기준 화면을 제시하고, 다른 화면을 그 기준으로 맞추게 한다.
- hover preview, 카드 확대, 16:9 썸네일처럼 상호작용과 시각 규칙을 연결해 생각한다.
- 색상 베리에이션을 시도하되 촌스럽거나 어두워졌다고 판단되면 빠르게 기준을 재조정한다.
- "등록 페이지 카드에는 hover가 필요 없다"처럼 컴포넌트 재사용의 부작용을 맥락 기준으로 잘라낸다.
- 작업이 쌓이면 GitHub 이슈, 커밋, 문서까지 남기려 한다.

### 오늘의 교훈

- Streamlit UI의 미세 정렬 문제는 CSS 값 하나가 아니라 `st.columns`, `st.container(key=...)`, iframe custom component, 내부 wrapper가 같이 만든 결과다.
- 같은 행으로 읽혀야 하는 요소는 실제 구조에서도 같은 컨테이너 안에 있어야 한다. 프로젝트 상세의 조회수/공개/링크복사/좋아요 정리는 이 원칙을 적용한 사례다.
- 공통 카드 컴포넌트라도 화면 맥락별로 상호작용 scope를 분리해야 한다. 홈 갤러리 hover preview가 등록 페이지 미리보기까지 번지면 좋은 기능이 아니라 불필요한 소음이 된다.
- 색상 베리에이션은 개수를 늘리는 것보다 제품 톤과 정보 가독성을 지키는 것이 먼저다.
- 문서는 작업이 끝난 뒤의 부가물이 아니라 다음 작업을 빠르게 시작하게 하는 인터페이스다.
- 리팩토링은 "동작은 같은데 파일만 나뉜 상태"로 끝나지 않는다. HTML 조각을 합치는 방식, Streamlit wrapper 수, custom component iframe의 위치가 달라지면 화면 결과도 달라질 수 있다.
- 문제가 재발했을 때 사용자가 "막 수정하지 말고 구조를 파악하라"고 제동을 건 것은 중요했다. 이 제동 덕분에 홈 히어로 raw HTML 노출과 상세 액션바 정렬 문제를 보정값이 아니라 구조 기준으로 다시 볼 수 있었다.
- 문서가 있어도 의사결정 순간에 체크포인트로 쓰지 않으면 같은 실수를 반복한다. "문서 업데이트해야지"처럼 사용자가 범위를 좁히면 문서만 반영하고 멈춰야 하며, 테스트·커밋·푸시는 각각 다시 확인받아야 한다.

### 다음 실험

- 큰 UI 변경 전에는 기준 화면, 유지할 컴포넌트, 버릴 컴포넌트를 먼저 한 줄로 정의한다.
- Streamlit wrapper가 관여하는 정렬 문제는 초기부터 DOM/좌표 측정을 병행한다.
- 공통 컴포넌트에 새 인터랙션을 추가할 때는 "어느 화면에서만 켜지는가"를 함께 설계한다.
- 리팩토링 직후에는 주요 화면을 "사용자 시나리오" 기준으로 다시 훑는다. 단위 테스트가 통과해도 HTML 렌더링, 이미지 표시, 칩 정렬처럼 시각 구조의 회귀는 별도 확인이 필요하다.
- 작업 단계 사이에는 멈춤 질문을 둔다. 문서 반영 후에는 "다음은 테스트인데 진행할까요?", 테스트 후에는 "이제 커밋할까요?"처럼 사용자의 다음 동사를 기다린다.
