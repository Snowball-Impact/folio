# FOLIO — 관리자 페이지 PRD

**문서 상태:** MVP 확정  
**기능 범위:** FOLIO 통합 운영 Admin  
**원칙:** Simple is Best. 관리자 페이지 자체를 별도 제품처럼 확장하지 않고, MVP 운영에 꼭 필요한 사후 관리 기능만 제공한다.

---

## 1. 목적

FOLIO의 프로젝트, 커뮤니티, 댓글, 사용자를 한 곳에서 확인하고 문제가 있는 콘텐츠를 최소한의 기능으로 사후 관리한다.

관리자 페이지는 승인·심사 시스템이 아니다.

> **조회 → 확인 → 필요 시 숨김/공개 또는 삭제**

이 흐름을 핵심으로 한다.

드물게 발생하는 고급 운영 작업은 별도 기능을 개발하지 않고 당분간 Supabase에서 직접 처리한다.

---

## 2. 정보 구조

```text
/admin

Overview
├── 프로젝트 관리
├── 커뮤니티 관리
├── 댓글 관리
├── 신고 관리
└── 사용자 관리
```

별도의 공지 관리 메뉴는 만들지 않는다.

공지는 `커뮤니티 관리`에서 작성·관리한다.

---

## 3. 공통 UI 구조

Admin은 사용자용 FOLIO와 분리된 운영 화면으로 구성한다.

```text
┌───────────────┬─────────────────────────────────────┐
│ FOLIO ADMIN   │                                     │
│               │  현재 관리 화면                     │
│ Overview      │                                     │
│ 프로젝트      │                                     │
│ 커뮤니티      │                                     │
│ 댓글          │                                     │
│ 사용자        │                                     │
│               │                                     │
│ ← FOLIO       │                                     │
└───────────────┴─────────────────────────────────────┘
```

### 원칙

- 좌측 Admin Navigation 사용
- Desktop First
- 기존 FOLIO 디자인 시스템 최대한 재사용
- 관리 목록은 테이블 중심
- 모든 관리 화면에서 동일한 Interaction 패턴 사용
- 모바일은 별도 최적화하지 않고 깨지지 않는 수준만 지원

## 4. Overview

### 목적

서비스 운영 현황을 빠르게 확인하고 각 관리 화면으로 이동한다.

상세 Analytics 기능은 제공하지 않는다.

### 요약 지표

```text
사용자
프로젝트
커뮤니티 게시글
댓글
```

각 항목은 전체 수량만 표시한다.

### 최근 활동

- 최근 등록 프로젝트
- 최근 커뮤니티 게시글
- 최근 가입 사용자

각 영역에는 최근 데이터 일부만 표시하고 필요하면 해당 관리 화면으로 이동한다.

### 와이어프레임

```text
FOLIO ADMIN

Overview

서비스 운영 현황

┌────────────┐ ┌────────────┐
│ 사용자     │ │ 프로젝트   │
│    128     │ │     47     │
└────────────┘ └────────────┘

┌────────────┐ ┌────────────┐
│ 게시글     │ │ 댓글       │
│     31     │ │     86     │
└────────────┘ └────────────┘


최근 등록 프로젝트
────────────────────────────────
SmartHRD            사용자A      08.23
Sales Dashboard     사용자B      08.22
                         [전체 보기]


최근 커뮤니티 게시글
────────────────────────────────
[질문] Gateway 연결 질문        08.23
[기타] 포트폴리오 피드백        08.22
                         [전체 보기]


최근 가입 사용자
────────────────────────────────
사용자C                        08.23
사용자D                        08.22
                         [전체 보기]
```

### MVP 제외

- 차트
- 기간별 추이
- 전주/전월 대비
- MAU/WAU
- 상세 이벤트 분석
- 조회수 분석

이러한 분석은 기존 Analytics 도구를 사용한다.

## 5. 프로젝트 관리

### 목적

등록된 프로젝트를 확인하고 운영상 문제가 있는 프로젝트를 숨김 또는 삭제한다.

### 목록 정보

- 프로젝트명
- 작성자
- 등록일
- 조회수
- 상태

### 기본 기능

- 검색
- 프로젝트 보기
- 숨김
- 공개
- 삭제

### 와이어프레임

```text
프로젝트 관리

등록된 프로젝트를 조회하고 관리합니다.

[검색________________________________]

전체 47개

────────────────────────────────────────────
프로젝트        작성자       등록일      상태
────────────────────────────────────────────
SmartHRD        사용자A      08.23       공개    ⋮
Sales BI        사용자B      08.22       공개    ⋮
Test            사용자C      08.20       숨김    ⋮
────────────────────────────────────────────
```

### Action Menu

공개 프로젝트:

```text
프로젝트 보기
────────────
숨김
삭제
```

숨김 프로젝트:

```text
프로젝트 보기
────────────
공개
삭제
```

### 정책

관리자가 다른 사용자의 프로젝트 내용을 직접 수정하는 기능은 제공하지 않는다.

운영 원칙은:

> **관리자는 콘텐츠를 관리하지만 작성자를 대신해 콘텐츠를 수정하지 않는다.**

---

## 6. 커뮤니티 관리

### 목적

커뮤니티 게시글을 조회하고 운영상 문제가 있는 콘텐츠를 관리한다.

### 목록 정보

- 카테고리
- 제목
- 작성자
- 작성일
- 상태

### 필터

```text
전체 / 공지 / 질문 / 팁·노하우 / 기타
```

### 기능

일반 게시글:

- 게시글 보기
- 숨김
- 공개
- 삭제

관리자 공지:

- 보기
- 수정
- 상단 고정 / 해제
- 삭제

### 공지 작성

커뮤니티 관리 상단에 다음 CTA를 제공한다.

```text
[+ 공지 작성]
```

별도의 공지 관리 메뉴는 만들지 않는다.

### 정책

관리자는 일반 사용자가 작성한 게시글의 내용을 직접 수정하지 않는다.

관리자가 작성한 공지만 수정할 수 있다.

---

## 7. 댓글 관리

### 목적

프로젝트와 커뮤니티에서 작성된 댓글을 한 화면에서 확인한다.

### 핵심 원칙

**새로운 댓글 관리 정책을 만들지 않는다.**

기존 프로젝트 상세페이지에서 이미 구현된 댓글 정책과 기능을 재사용한다.

### 필터

```text
전체 / 프로젝트 / 커뮤니티
```

### 목록 정보

- 댓글 일부
- 작성자
- 위치
- 작성일

### 기능

- 원문 보기
- 기존 댓글 정책에 따른 관리

커뮤니티 댓글 기능 공통화 과정에서도 기존 프로젝트 댓글 데이터와 기능의 하위 호환성을 보장한다.

## 8. 사용자 관리

### 목적

가입한 사용자의 기본 활동 현황을 조회한다.

MVP에서는 사용자 제재 시스템을 구현하지 않는다.

### 목록 정보

- 사용자
- 가입일
- 프로젝트 수
- 커뮤니티 게시글 수
- 댓글 수

### 와이어프레임

```text
사용자 관리

가입한 사용자를 확인합니다.

[검색________________________________]

전체 128명

──────────────────────────────────────────────
사용자       가입일       프로젝트   게시글   댓글
──────────────────────────────────────────────
사용자A      07.15           4         3       12
사용자B      08.01           2         1        5
사용자C      08.12           0         4        8
──────────────────────────────────────────────
```

### 제외

- 사용자 상세 페이지
- 계정 정보 수정
- 경고
- 기간 정지
- 영구 정지
- 회원 삭제
- 관리자 권한 부여 UI

필요한 경우 초기에는 Supabase에서 직접 처리한다.

---

## 9. 신고 관리

### 목적

상세페이지에서 접수된 콘텐츠 신고를 운영자가 확인하고 처리 상태를 관리한다.

신고는 프로젝트 소유자에게 직접 전달하지 않는다.

> **사용자 신고 → 운영자 확인 → 필요 시 숨김/삭제 또는 기각**

### 신고 대상

MVP의 1차 신고 대상은 프로젝트 상세 콘텐츠다.

대표적인 사유:

- 대시보드/임베딩이 열리지 않음
- 보고서 보기 링크가 죽어 있음
- 제목이나 설명이 실제 내용과 다름
- 부적절한 콘텐츠
- 기타

### 정책

- 로그인 사용자만 신고할 수 있다.
- 신고 조회는 관리자만 가능하다.
- 신고 상태 변경은 관리자만 가능하다.
- 프로젝트 소유자는 신고 목록과 신고자 메모를 직접 조회할 수 없다.
- 운영자가 필요하다고 판단할 때만 별도 연락 또는 프로젝트 숨김/삭제 조치를 한다.
- 신고는 사전 승인 흐름이 아니라 사후 관리 신호다.

### 상태

```text
open
reviewing
resolved
dismissed
```

### 목록 정보

- 신고 대상 프로젝트
- 신고 사유
- 메모
- 신고자
- 접수일
- 상태

### 기능

- 상태 필터
- 프로젝트 상세로 이동
- 처리 중으로 변경
- 해결 처리
- 기각 처리

### 데이터 모델 방향

신고 접수는 별도 운영 테이블로 관리한다.

개념적 테이블:

```text
content_reports
├── id
├── project_id
├── reporter_id
├── reason
├── details
├── status
├── created_at
└── updated_at
```

RLS 기준:

- insert: 로그인 사용자 본인 신고만 허용
- select: 관리자만 허용
- update: 관리자만 허용

### MVP 제외

- 신고 접수 즉시 이메일 알림
- 프로젝트 소유자 자동 알림
- 사용자 이의제기
- 신고자/작성자 간 직접 대화
- 자동 숨김
- 반복 신고 기반 자동 제재

## 10. 관리자 접근 권한

Admin 경로:

```text
/admin
```

접근 흐름:

```text
/admin
  ↓
로그인 확인
  ↓
관리자 권한 확인
  ├── admin → 관리자 페이지
  └── user  → 접근 거부
```

비로그인 사용자는 기존 로그인 Flow로 연결한다.

일반 사용자에게는 다음과 같이 안내한다.

```text
관리자 권한이 없습니다.

[홈으로]
```

### 관리자 식별

기존 사용자 구조에 관리자 식별 값이 없다면 최소한 다음 수준으로 구현한다.

```text
role
├── user
└── admin
```

초기 관리자 권한은 DB에서 직접 설정한다.

관리자 권한을 관리하는 별도 UI는 만들지 않는다.

### 보안

관리자 권한은 화면에서만 검사하지 않는다.

Supabase RLS 또는 서버 측 권한 검증에서도 관리자 작업을 보호해야 한다.

## 11. 숨김 / 공개 정책

프로젝트와 커뮤니티 게시글에서 동일한 개념을 사용한다.

### 공개

정상적으로 사용자에게 노출되는 상태.

### 숨김

관리자가 운영 목적으로 일시적으로 노출을 중단한 상태.

```text
공개
 ↓
숨김
 ↓
사용자에게 비노출
 ↓
필요 시 다시 공개
```

숨김은 가역적인 운영 조치다.

관리자 운영에서는 삭제보다 숨김을 우선한다.

---

## 12. 삭제 정책

삭제는 숨김보다 강한 조치로 사용한다.

삭제 전 확인 UI를 제공한다.

```text
삭제하시겠습니까?

삭제 후 서비스에서 다시 확인할 수 없습니다.

[취소] [삭제]
```

가능하면 DB에서는 Soft Delete를 사용한다.

연결된 댓글 등 다른 사용자 데이터가 존재하는 경우 Cascade Delete로 함께 제거하지 않는 것을 우선한다.

---

## 13. 관리자 조치 알림

MVP에서는 관리자 조치에 대한 별도의 사용자 알림 시스템을 만들지 않는다.

제외:

- 이메일 알림
- Push
- 알림센터
- 숨김 사유 입력
- 이의제기 시스템

사용자가 자신의 콘텐츠 관리 화면에서 현재 상태를 확인할 수 있는 기존 구조가 있다면 이를 활용한다.

---

## 14. 데이터 모델 방향

Admin 전용 데이터베이스를 별도로 만들지 않는다.

기존 서비스 데이터에 필요한 최소 운영 상태만 추가하거나 기존 상태값을 재사용한다.

### 프로젝트

현재 프로젝트 공개 상태 구조를 먼저 확인한다.

기존 상태값이 있다면 새 컬럼을 만들지 않고 재사용 또는 최소 확장한다.

개념적으로 필요한 상태:

```text
public
hidden
```

### 커뮤니티

기존 커뮤니티 PRD의 `community_posts` 구조를 사용한다.

필요 시 관리자 숨김을 위한 최소 상태를 추가한다.

```text
is_hidden
```

### 댓글

기존 댓글 DB와 정책을 재사용한다.

### 신고

상세페이지 신고 접수와 Admin 신고 관리를 위해 `content_reports` 계열 테이블을 사용한다.

신고 조회와 상태 변경은 운영자 전용 기능으로 둔다.

프로젝트 소유자에게 신고 row를 직접 노출하지 않는다.

### 사용자

필요 시 기존 `profiles`에 관리자 식별 값을 추가한다.

```text
role = user | admin
```

실제 구현 전 Codex는 현재 Supabase 스키마를 먼저 확인하고 중복 컬럼이나 불필요한 마이그레이션을 만들지 않는다.

---

## 15. 공통 관리 Interaction

프로젝트와 커뮤니티는 가능한 한 같은 관리 패턴을 사용한다.

```text
목록
 ↓
검색 / 필터
 ↓
대상 확인
 ↓
⋮
├── 보기
├── 숨김 / 공개
└── 삭제
```

같은 동작을 화면마다 다른 UI로 구현하지 않는다.

---

## 16. 반응형 정책

Admin은 **Desktop First**로 개발한다.

모바일에서는:

- 화면이 깨지지 않아야 한다.
- 테이블은 필요하면 가로 스크롤을 허용한다.
- 좌측 Navigation은 접을 수 있도록 한다.

별도의 모바일 Admin UX는 설계하지 않는다.

---

## 17. MVP 제외 범위

이번 Admin MVP에서는 다음 기능을 구현하지 않는다.

- 프로젝트 등록 승인
- 게시글 사전 승인
- 자동 제재가 포함된 복잡한 신고 워크플로우
- 사용자 경고
- 기간 정지
- 영구 정지
- 회원 삭제
- 사용자 상세 페이지
- 관리자 권한 관리 UI
- 관리자 등급
- 운영자별 권한 분리
- 대량 이메일
- Push
- 관리자 조치 알림센터
- 숨김 사유 관리
- 이의제기
- 상세 Analytics
- 차트
- MAU/WAU 분석
- 감사 로그 시스템
- 복잡한 운영 Workflow

실제 운영에서 필요성이 확인되면 이후 추가한다.

## 18. Acceptance Criteria

### 관리자 접근

```text
관리자 로그인
→ /admin 접근
→ Overview 확인
```

일반 사용자가 `/admin`에 접근하면 Admin 데이터와 기능에 접근할 수 없어야 한다.

Supabase 권한에서도 동일하게 차단되어야 한다.

### 프로젝트 관리

```text
프로젝트 목록 조회
→ 프로젝트 원문 확인
→ 숨김
→ 서비스에서 비노출 확인
→ 다시 공개
```

필요한 경우 삭제할 수 있어야 한다.

### 커뮤니티 관리

```text
커뮤니티 목록 조회
→ 게시글 원문 확인
→ 문제 게시글 숨김/삭제
```

관리자는:

```text
공지 작성
→ 상단 고정
→ 수정
→ 고정 해제
```

가 가능해야 한다.

### 댓글 관리

프로젝트와 커뮤니티 댓글을 한 곳에서 확인하고 기존 댓글 관리 정책에 따라 처리할 수 있어야 한다.

기존 프로젝트 댓글 기능 및 데이터에 회귀 문제가 없어야 한다.

### 신고 관리

관리자는 접수된 신고를 조회하고 상태를 변경할 수 있어야 한다.

```text
프로젝트 상세에서 신고 접수
→ Admin 신고 관리 목록에 open 상태로 표시
→ 프로젝트 원문 확인
→ reviewing / resolved / dismissed 중 하나로 상태 변경
```

일반 사용자와 프로젝트 소유자는 Admin 신고 목록과 신고 메모에 접근할 수 없어야 한다.

### 사용자 관리

사용자를 검색하고 다음 정보를 확인할 수 있어야 한다.

- 가입일
- 프로젝트 수
- 게시글 수
- 댓글 수

## 19. 최종 Admin MVP

```text
FOLIO ADMIN

Overview
│
├── 프로젝트 관리
│    └── 조회 / 숨김 / 공개 / 삭제
│
├── 커뮤니티 관리
│    └── 조회 / 숨김 / 공개 / 삭제
│       + 공지 작성 / 수정 / 상단 고정
│
├── 댓글 관리
│    └── 기존 댓글 정책 재사용
│
├── 신고 관리
│    └── 조회 / 상태 변경 / 프로젝트 원문 확인
│
└── 사용자 관리
     └── 조회
```

## 20. MVP 핵심 정의

> **FOLIO Admin은 서비스 콘텐츠와 사용자를 한 곳에서 확인하고, 문제가 있는 콘텐츠를 최소한의 조치로 사후 관리하는 운영 도구다.**

Admin 자체를 별도 제품으로 확장하지 않는다.

운영에 꼭 필요한 기능은 Admin에서 처리하고, 사용 빈도가 낮거나 복잡한 고급 작업은 당분간 Supabase에서 직접 처리한다.
